# Security review — 2026-10-28 (Phase 3, adversarial pass)

**Scope:** the integrated `develop` branch: API (all modules), worker, console, nginx/compose
configuration, CI. **Method:** read every trust-boundary entry point as an attacker would
([threat model](threat-model.md) §3), look for concrete, exploitable paths rather than checklist
items, then fix, write a regression test, and prove the test fails without the fix (mutation check).
Load-related findings came from the k6 runs ([performance.md](../operations/performance.md)).

## Verified as sound (no change needed)

- **Webhook HMAC:** constant-time compare, timestamp bound into the signature, strict header formats, generic 401, 404 for unknown sources (including `constructor`/`__proto__`-style IDs).
- **Access control:** deny-by-default route policies (the server refuses to start otherwise), authorization in `onRequest` _before_ body parsing (no schema leaks to anonymous callers), RBAC matrix test over every route.
- **Sessions:** HS256 pinned, `iss`/`aud` checked, refresh rotation with reuse detection under a row lock (race-tested), CSRF header + Origin allow-list on cookie endpoints, access token in memory only (the console's only `localStorage` use is the theme preference).
- **Injection:** all SQL is parameterized by Kysely; `ILIKE` input is escaped (`%`, `_`, `\`); no `eval`/`Function`/`vm`/`dangerouslySetInnerHTML` anywhere in production code; predicate regexes pass a ReDoS guard; playbook YAML parsing rejects tags, caps aliases and size.
- **Edge:** strict CSP for the SPA, `frame-ancestors 'none'`, HSTS on TLS, `X-Forwarded-For` overwritten (not appended), per-path body limits, `limit_req` on login and webhooks.
- **Supply chain:** `pnpm audit` clean, exact pins, CodeQL, gitleaks, Trivy on both images (0 fixable HIGH/CRITICAL in CI), SBOMs.

## F4 in detail

The trigger stopped _accidental_ and _SQL-injection-style_ tampering, because an `UPDATE audit_log`
issued through the app is rejected. It didn't stop an attacker with arbitrary SQL as the table
owner, who can `ALTER TABLE audit_log DISABLE TRIGGER`. The review first documented a manual fix;
on 2026-10-29 it was implemented as [ADR-0092](../adr/0092-separate-migration-and-runtime-database-roles.md):
a one-shot migrate step runs as the owner, and the API and worker connect as `spine_app`
(member of `spine_runtime`, insert-only on `audit_log`). On the live stack:

```
spine=> update audit_log set action='forged' where id = …;
ERROR:  permission denied for table audit_log
spine=> alter table audit_log disable trigger audit_log_no_update;
ERROR:  must be owner of table audit_log
```
